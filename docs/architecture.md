# Architecture

## Responsibilities

- **Hub config** defaults to the curated child MCPs in `config/hub.example.json` and their tool allowlist. Known sibling repos are discovered at startup; private config overrides defaults, including explicit disables.
- **Per-MCP private config** holds local settings or references to credentials needed by one child MCP.
- **Hub runtime** validates config, connects to child MCPs, exposes allowlisted tools, routes calls, and writes audit events.
- **Shared service** keeps one Hub runtime and one connection per child alive for the signed-in Windows user. It exposes authenticated Streamable HTTP and retains the legacy stdio endpoint; a thin stdio bridge lets clients share the service.
- **Issue jobs** coordinate bounded logs, source, Jira, and PR specialists. Job details are encrypted in SQLite (Windows DPAPI on Windows, user-only `0600` Fernet key on POSIX) and retained for 30 days.
- **Desktop app** reports Hub and child readiness and controls the per-user scheduled task through the local HTTP API.
- **Child MCP** owns its domain logic, credentials, and upstream service behavior.
- **Agent docs** explain tool purpose and operational rules; they do not enforce access control. The Hub must enforce the configured allowlist.

## Module layout

The leaf modules `jsonio`, `textnorm`, `clients`, `tool_meta`, and `progress` import nothing from the Hub. `tests/test_module_boundaries.py` enforces this and the other import rules.

Dependencies flow one way: `child_requirements` (a leaf, importing nothing from the Hub) → `config` → `settings` / `client_profiles` → `audit` / `extensions` / `hub_settings` → `results/*` and `planning/*` (below `server`, and never importing each other the wrong way) → `server` (the runtime, composed from mixins: `child_lifecycle`, `tool_pins`, `batch`, `planning/hub_plan`, `results/runtime`, `call_observers`; with `children`, `child_logs`, `config_sources`, `events`, `schema_rewrite`, `instructions`) → `http` → `service`, which starts through `bootstrap`. `dashboard`, `jobs`, `agents`, `bridge`, `preflight`, and `control` use only public functions and methods of those modules; `activity_ui` is imported only by `service.py`. `desktop` imports nothing from `mcp_hub` outside `mcp_hub.desktop` (a test checks it): it finds the Hub through the connection file the service writes and talks to it only through its HTTP API, so it ships as its own installer. Every module below is imported by at least one test.

## Core and extensions

The core tool-call path is `HubRuntime.call_child_tool`: route lookup, one audit line, the child call under its timeout (`_invoke_child`, the single point a result cache wraps), and one audit line for the outcome. `HubRuntime.observers` is empty by default, so the core path has no activity tracking, client tracking, or store access. Core modules (`server`, `http`, `extensions`, `dashboard/api.py`, `jobs`) never import an extension.

**Usage policy.** `HubRuntime.call_tool` checks a client's direct child call, and every call of a `hub__batch`, against the plan named by its `hub_plan_id` (`policy.check`) before `call_child_tool`, then records the outcome. The job runner calls `call_child_tool` directly, so investigation jobs keep their own policy. See [usage-policy.md](usage-policy.md).

**Client workflow harness.** Each shipped playbook owns a JSON workflow graph. planning/workflow_definition.py validates and compiles explicit subflows; planning/workflow_scope.py validates fill-once inputs and extracts bounded evidence anchors. planning/workflow.py keeps graph progress on the bounded Plan, and planning/workflow_runtime.py routes MCP operations and serialized direct/batch execution. Missing context waits for the user; same-scope continue_from adds declared cache-refresh writes without replay and retires the predecessor. The client controls reasoning and reports semantic findings; investigation jobs retain their existing loop. See [the workflow contract](usage-policy.md#client-workflow-harness).

**Result cache.** `_invoke_child` sends a read-only tool (`readOnlyHint=true`) with a `cacheSeconds` TTL through `ResultCache.get_or_call`: a fresh successful result is returned without calling the child (`tool.call.cached`), and identical concurrent calls share one child call. Any call to a child's tool that is not read-only drops that child's cached entries. The rules and per-child defaults are in [mcps/README.md](mcps/README.md#hub-result-cache); agents still read child caches first ([client-rules.md](client-rules.md)).

**Result shape.** A result is condensed only when its tool is read-only, the result is text, the tool declares no `outputSchema`, and the result has no `structuredContent` or non-text block (`result_shape.is_condensable`). Any other result passes through unchanged, and so does a text result that the full-result store cannot hold (one entry over `bitnet.fullResultMaxBytes`). A condensed result keeps its footer and carries `_meta["mcp-hub/condensed"]` = `{result_id, kept, total}`. Batch packing applies the same rule.

**Progress and `_meta`.** A client's `progressToken` receives the child's progress for that call, on the request's own stream. The client's connection-owned `_meta` keys (`protocolVersion`, `clientInfo`, `clientCapabilities`) are not forwarded to the child; other keys are.

**Tool checks and redaction.** Each child tool definition is pinned by a SHA-256 hash of its name, description, input and output schemas, and annotations (`tool_pins.py`; the pin file holds hashes only, and is `config/private/tool_pins.json`; `security.toolPinMode`). A changed definition writes `tool.definition.changed` and appears under `tool_pins` in `hub__status`; in `warn` mode the tool keeps running, while in `enforce` mode changed tools and hidden-Unicode descriptions are omitted from routes until accepted via `POST /dashboard/api/security/pins/accept` or `hubctl pins` (`tool.pins.accepted`). Call arguments are checked against the child's input schema (`protocol.validateArguments`): `warn` logs `tool.arguments.invalid` and runs the call; `enforce` rejects invalid arguments before calling the child. Outbound text in tool results and proxied text resources is scrubbed of configured secrets and high-confidence credential patterns when `security.redactResults` is `true`.

**Local model hooks.** Core defines hook interfaces in `extensions.py` (`PlanAssistant`, `ResultCondenser`, `DraftSummarizer`), deterministic condensing (`RuleCondenser` in `condense.py`), and `full_results.py` (`FullResultStore`). Even without the `bitnet` extension, `service.py` and the stdio entrypoint enable core structural condensing and `hub__get_full_result`. When `bitnet` is requested, `service.py` replaces `runtime.condenser` with `BitnetCondenser` and wires `PlanAssistant` and `DraftSummarizer` (`bitnet.md`). See [bitnet.md](bitnet.md).

**Processing metadata.** Core also defines frozen `ProcessingEvent` and optional `ProcessingObserver` contracts in `extensions.py`. Runtime and job stages report fixed codes through these contracts, without importing BitNet or exposing call data. `processing_step` preserves stage results and exceptions; observer failures cannot fail a stage. BitNet installs `ProcessingFeed` (`bitnet/processing.py`) on runtime and job runner, and exposes it through authenticated SSE in `bitnet/setup.py`. The feed owns only a three-event memory ring and bounded subscriber queues, independently of Activity UI and its database. See the owning [stream contract](bitnet.md#processing-stream).

An extension implements `CallObserver` (`call_started`, `call_finished`, `client_seen`; metadata only, never arguments or results) and may contribute a `DashboardExtension` (local API routes, status fields, and the `hubctl` flags that keep it on across a Hub restart). Observer hooks run on the event loop, so they only update memory or enqueue; a failing observer is logged (`extension.observer.failed`) and never fails the call.

Start-time flow: `hubctl start|restart|install -Ui` writes `config/private/launch.json` (`{"extensions": ["activity-ui"]}`) right before starting the task, and removes it without `-Ui`. `service.py` reads and deletes the file at start (`extensions.read_launch_extensions`; an unreadable or invalid file is logged as `launch.file.invalid` and means fast mode) and, only when `activity-ui` is requested, imports `activity_ui` and calls `install(runtime, store=..., audit=...)`. That adds the observer, a wrapper around the Hub's `subscriptions/listen` handler that records open listen streams as connected clients (the Hub answers `subscriptions/listen` with or without tracking), `ClientSessionMiddleware` inside the bearer check, the `/dashboard/api/activity` and `/dashboard/api/activity/stream` local API routes, and the `activity`/`clients` status fields consumed by desktop. `/dashboard/api/status` always reports `extensions.activityUi`. With activity tracking on, finished calls are queued in memory and written by a background task in batches (up to 50 rows or 1 second) with one multi-row INSERT via `asyncio.to_thread`; the queue is flushed after the job runner closes at shutdown.

`scripts/bench_call_path.py` measures sequential tool-call latency through the HTTP app with the activity UI off and on. `scripts/call_report.py` reads the audit log and shows where real tasks spend their time: a client's thinking between two calls usually costs several times the call itself, which is why `hub__batch` exists.

## Request path

Direct call: `AI client → authenticated shared Hub → child MCP client → child MCP tool → metadata-only Hub audit log`

Investigation call: `AI client → job queue → fixed specialist roles → allowlisted child MCP tools → encrypted job result → coordinator summary`

Every exposed tool should map to exactly one child server and tool name. Use namespaced exposed names such as `serverId__toolName` to avoid collisions. A feature may expose tools from multiple child MCPs. Keep the initial design as a curated proxy; add cross-server composite tools only when a real workflow needs them.

## Failure handling and child selection

- **Isolation.** Each enabled child runs under its own `ChildSupervisor` (`children.py`): an asyncio task that owns the child's MCP client, its transport task groups, and its process. A child failure (a crash, a closed session, an error in the transport reader) ends only that task's session; it never reaches the service task that runs uvicorn, or another child. Child stdout is decoded with `encoding_error_handler="replace"`, so non-UTF-8 output becomes an unparsable line the SDK skips instead of an exception.
- **Start.** All children connect in parallel. Each attempt (start the process, MCP handshake, `list_tools`) is bounded by the child's `connectTimeoutSeconds` (default 120); a timed-out or failed attempt closes the process it started. The Hub serves once every child has finished its first attempt or `children.startupWaitSeconds` (default 10) has passed, whichever comes first. A child still connecting then joins the tool list when it connects (`hub.tools.registered`). A failed first attempt is logged (`server.connect.failed` or `server.list_tools.failed`), its tools are skipped (`route.skipped`), and the child is retried in the background like a lost one. With no available child tools, the Hub still exposes `hub__status`.
- **Reconnect.** When a connected child's session ends (the process exits, its stdout closes, or the transport fails), the Hub logs `server.disconnected` and retries after 1 s, doubling the delay after each failed attempt up to 60 s (`server.reconnect.failed` carries `retry_in_seconds`). A session that stayed up for less than 60 s counts as a failed attempt, so a child that crashes right after connecting is not restarted every second. A successful attempt logs `server.reconnected`, lists the child's tools again, and rebuilds the routes: a tool the child no longer lists is reported with `route.skipped` and calls to it are denied; a tool that appears is exposed, and `hub.tools.registered` lists the new set. Each change to the exposed tools, or to a tool definition, is announced once per `protocol.listChangedDebounceSeconds` window as `notifications/tools/list_changed` on the Hub's `subscriptions/listen` stream (audited as `tools.list_changed.published`, also when no listen stream is open). A child that sends its own `tools/list_changed` is relisted the same way, without a reconnect. A 2025-era client holds no listen stream and the Hub sends it nothing, so it sees the change on its next `tools/list`; this is not covered by a test. `tools/list` is ordered: `hub__status`, `hub__plan`, `hub__batch`; then each child's tools in config order, each sorted by name; then `hub__get_full_result` when its store is on; then the job tools. It carries `ttlMs` from `protocol.toolsListTtlMs`. Shutdown stops every supervisor and its process; nothing reconnects after it.
- **Calls while a child is down** return an error result immediately (`Child MCP <server-id> is reconnecting; retry shortly. request_id=<n>`) and are logged as `tool.call.failed` with `error_type=ChildUnavailable`; they never wait for the call timeout. The hot path checks only whether the child has a live client (a dict lookup).
- `hub__status` and the desktop status API report detected sibling count, connected count, and each known child's state: `connected`, `connecting` (first attempt in progress), `reconnecting` (waiting to retry after a failed attempt or a lost session), `disabled`, `credentials required`, or `unavailable` (configured but not started). A child with unfilled `<SET_BY_USER>` placeholders in its private config is marked `credentials required`; its tools are not exposed. The built-in templates use empty values instead, so a child without Hub credentials still starts and uses its own local files (see [Configuration sources](child-mcp-compatibility.md#configuration-sources)). Detailed diagnostics are in the Hub log and the child's stderr log (`logs/children/<server-id>.log`, see [security-and-logging.md](security-and-logging.md)).
- Each call is limited by the child's `timeoutSeconds` (default 60); a timeout is logged as `tool.call.failed` with `error_type=TimeoutError`. A failure raised as an exception group is logged by its first leaf exception, so `error_type` names the cause.
- The Hub exposes one MCP prompt per connected child, named after its server ID. Clients that support prompts show it as a slash command (the exact format is client-defined); it tells the Agent which Hub tools belong to that child and includes `docs/mcps/<server-id>.md`.
- On connect, the Hub sends server instructions, essentials first: the summary (under 512 characters, `INSTRUCTIONS_SUMMARY` in `server.py`), the tool list per child, and then [client-rules.md](client-rules.md), read at startup. `instructions.build_instructions` keeps the whole text to 4,096 characters (the limit Claude Code applies); a section that does not fit ends with a note that names where the rest is: `+N more; see tools/list` for the tool list, `+N more lines in docs/client-rules.md` for the rules. The sections after a cut one are left out. The text has no live connection counts; `hub__status` reports them. Clients that ignore server instructions get the same rules from the always-on rule installed by [connecting-a-client.md](connecting-a-client.md) step 7.

## Child servers (local stdio and remote Streamable HTTP)

Children run over `stdio` or `streamable-http`. For `stdio`, the Hub launches each one with an argument array (never a shell string) in the child's `cwd`, passing only the MCP SDK's default safe variables, the `inheritEnv` names, and the child's `env` values; declarative `useHubVenv` and `pythonPath` options let Python children share the Hub's `.venv` without hardcoded IDs. For `streamable-http`, the Hub connects with `trust_env=False` to an `https://` endpoint or loopback `http://` endpoint and adds sensitive `headers` values to the redaction set. Child repositories sit next to this repo (`../<repo>`), and toggling `servers.<id>.enabled` through the local settings API hot-reloads that child via `HubRuntime.reload_server` (`server.reloaded`) without restarting the Hub. An explicit `MCP_HUB_CONFIG` retains the private-manifest-only behavior.

## Setup and first-run checks

`Setup.cmd` runs `scripts/setup.ps1`, a thin layer outside `src/mcp_hub/`. It asks nothing and only calls what already exists: `git clone`, `hubctl install` (environment, `preflight --install`, service, status app), and `scripts/smoke.py`.

- **One list of default children.** The default children and their GitHub `repository` addresses live only in `config/hub.example.json`; Setup reads them there and clones those missing next to this repo. A new default child is added there (and in `docs/mcps/`), never in `setup.ps1`; `scripts/check_docs.py` fails when a default child lacks either.
- **Installing stays in `prepare`.** What a child needs (runtime, packages, build) is declared in its `prepare` block and run by the preflight, one child after another. Setup adds no install steps of its own; a child that runs on the Hub's own `.venv` gets its packages from `pyproject.toml`.
- **Accounts never pass through Setup.** It does not open, read, write, print, or ask for account values or project paths, and does not launch a child's login screen. It only prints where the user fills them in, in each child's own repository. A child that has no account yet must still start and list its tools; its read-only check then says so and the smoke check reports `WARN` (not `FAIL`).
- **Smoke check.** `scripts/smoke.py` connects through the Hub like an MCP client and checks each child in turn: `PASS` (the check succeeded), `WARN` (the user has not filled in that child's account or project folders), or `FAIL` (not connected, tool missing, or the upstream rejected it). A child that fails or raises does not stop the next one. A last line checks the Hub itself (`hub__status`). The exit code is 1 only when something is `FAIL`.
- **AI clients.** Setup detects installed clients and copies one message (prompt A of [connecting-a-client.md](connecting-a-client.md)); the client edits its own config after asking the user.
- **No dependency on the core.** The scripts use only public commands and the Hub's MCP interface, so the core modules above do not import them.

## Shared Windows service

`scripts/hubctl.ps1 install` prepares a per-user Task Scheduler task named `mcp-hub` with limited privileges and starts `mcp-hub-service` through `pythonw.exe` without a console window, independently of terminal windows and battery power. Before every start, `hubctl` syncs the locked environment and runs `python -m mcp_hub.preflight --install`, which checks each enabled child's declared runtime (installing or upgrading it with winget when needed) and runs the child's own dependency step. Child `prepare` commands get the same environment as the child at runtime (`children.child_environment`: the MCP SDK's safe defaults, `inheritEnv`, and `env`), and executables are resolved only from absolute `PATH` entries, never the working directory (`preflight.find_executable`). The sign-in task and a restart after a crash start the service from `scripts/service_launcher.pyw`, not through `hubctl`, so the launcher first checks that the environment is current: it compares the SHA-256 of `uv.lock` with the stamp `.venv/.mcp-hub-lock.sha256`, which `start.ps1 -Prepare` (the one place that runs the locked sync, also for `hubctl`) writes after every successful sync. When they differ, for example after a `git pull` that added a dependency, the launcher runs that same sync before the service starts (it needs no `hubctl`); if the sync does not finish (offline, a file in use) the service still starts with the current environment and the failure is a line in `logs/mcp-hub-service.err`, retried at the next start. The launcher syncs only the Hub's Python environment; a child's own runtime and packages stay in its `prepare` step, run by `hubctl`. The service binds only to loopback (`127.0.0.1:8765`, from `config/private/service.json`), requires a bearer token for MCP, and keeps the original per-client stdio launcher. HTTP-capable clients can use `scripts/http_headers.ps1`; other clients use `scripts/start.ps1 -Bridge`, which forwards stdio MCP messages to the shared service. The desktop status app (`desktop/`) is a separate product with its own installer and sign-in entry; it reads the Hub's URL and admin token from the connection file and uses the authenticated local API. Its update workflow starts a detached Hub-owned updater and reads a bounded sanitized progress file under user app data so progress survives Hub restarts ([desktop-app.md](desktop-app.md)). Setup and migration are in [the shared-service runbook](operations/shared-agent-hub.md).

The job runner allows two active jobs, at most 20 queued jobs (`hub__submit_issue` and `hub__provide_job_input` return an error when the queue is full), a 15-minute investigation window, and 30 child-tool calls per job. Jobs missing an environment wait for validated input. Specialists are offered only their role's tools that the child marks read-only plus the Hub's encrypted cache-refresh allowlist (`jobs/policy.py`). A failed tool call (unknown or withheld tool, schema mismatch, child exception or error result, call cap) goes back to the model as an error tool message, so the specialist continues; only a provider error or its round limit ends it, and evidence it already stored is kept. When the window ends, unfinished specialists are cancelled and contribute the evidence they stored; the coordinator then gets up to 90 seconds (`COORDINATOR_SECONDS`) to summarize what exists, otherwise a fallback summary lists the findings and evidence IDs, and the job ends `partial`. A job waiting for write approval releases its active slot and takes one again after approval (specialists already running in that job continue); the wait still counts against its 15-minute window. While a job runs, its store and DPAPI work (events, child results, details, summaries, approvals) runs via `asyncio.to_thread`; only start-up recovery and cancellation bookkeeping run inline. `hub__get_job` returns the first 100 timeline events and every evidence ID of the job. On restart, active investigation state is marked interrupted and never replayed. A pending write can remain awaiting approval until 15 minutes after the job was created, then the job becomes `partial` (`approval.expired`); once approved, the exact stored operation is executed once and the job reports partial because its model investigation is not replayed. The browser approval UI has been removed; human approval works via the admin-authenticated local API (`/dashboard/api/jobs/pending`, `/dashboard/api/jobs/{job_id}/decision`, used by **mcp-hub Status** and `hubctl approvals`) or a one-time code passed to `hub__approve_job` (see [security-and-logging.md](security-and-logging.md)).

Each child MCP has a contract at `docs/mcps/<server-id>.md`; see [mcps/README.md](mcps/README.md). To add one, follow [adding-a-child-mcp.md](adding-a-child-mcp.md).

## Ticket-review source boundaries

Ticket-review explicitly enables multi_source and multi_ticket on its definition. An interaction-only node records the client-reported user confirmation. Context stores registered role aliases and selected related keys, never local repository roots. Source/Jira receipts retain alias/issue provenance; source path and attachment guards use that provenance. Existing single-project/single-ticket workflows do not inherit the expanded scope. See [ticket review](usage-policy.md#ticket-requirements-review).
