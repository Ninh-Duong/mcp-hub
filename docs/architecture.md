# Architecture

## Responsibilities

- **Hub config** defaults to the four curated child MCPs and their tool allowlist. Known sibling repos are discovered at startup; private config overrides defaults, including explicit disables.
- **Per-MCP private config** holds local settings or references to credentials needed by one child MCP.
- **Hub runtime** validates config, connects to child MCPs, exposes allowlisted tools, routes calls, and writes audit events.
- **Shared service** keeps one Hub runtime and one connection per child alive for the signed-in Windows user. It exposes authenticated Streamable HTTP and retains the legacy stdio endpoint; a thin stdio bridge lets clients share the service.
- **Issue jobs** coordinate bounded logs, source, Jira, and PR specialists. Job details are encrypted with Windows DPAPI in SQLite and retained for 30 days. Off Windows the store cannot encrypt, so `hub__submit_issue` refuses jobs with `investigation jobs require Windows DPAPI` and agent status reports `unavailable: windows-only`.
- **Dashboard** reports child and agent readiness, lists shared jobs, shows full pending-write previews with secrets masked, and controls the per-user scheduled task.
- **Child MCP** owns its domain logic, credentials, and upstream service behavior.
- **Agent docs** explain tool purpose and operational rules; they do not enforce access control. The Hub must enforce the configured allowlist.

## Module layout

Dependencies flow one way: `config` → `audit` / `extensions` → `server` (with `children`, `child_logs`, `result_cache`) → `http` → `service`. `dashboard`, `jobs`, `agents`, `bridge`, `preflight`, `control`, and `desktop` use only public functions and methods of those modules; `activity_ui` is imported only by `service.py`, and `desktop` talks to the Hub only through its HTTP API. Every module below is imported by at least one test.

## Core and extensions

The core tool-call path is `HubRuntime.call_child_tool`: route lookup, one audit line, the child call under its timeout (`_invoke_child`, the single point a result cache wraps), and one audit line for the outcome. `HubRuntime.observers` is empty by default, so the core path has no activity tracking, client tracking, or store access. Core modules (`server`, `http`, `extensions`, `dashboard/api.py`, `jobs`) never import an extension.

**Result cache.** `_invoke_child` sends a read-only tool (`readOnlyHint=true`) with a `cacheSeconds` TTL through `ResultCache.get_or_call`: a fresh successful result is returned without calling the child (`tool.call.cached`), and identical concurrent calls share one child call. Any call to a child's tool that is not read-only drops that child's cached entries. The rules and per-child defaults are in [mcps/README.md](mcps/README.md#hub-result-cache); agents still read child caches first ([client-rules.md](client-rules.md)).

An extension implements `CallObserver` (`call_started`, `call_finished`, `client_seen`; metadata only, never arguments or results) and may contribute a `DashboardExtension` (routes, status fields, and the `hubctl` flags that keep it on across a dashboard restart). Observer hooks run on the event loop, so they only update memory or enqueue; a failing observer is logged (`extension.observer.failed`) and never fails the call.

Start-time flow: `hubctl start|restart|open|install -Ui` writes `config/private/launch.json` (`{"extensions": ["activity-ui"]}`) right before starting the task, and removes it without `-Ui`. `service.py` reads and deletes the file at start (`extensions.read_launch_extensions`; an unreadable or invalid file is logged as `launch.file.invalid` and means fast mode) and, only when `activity-ui` is requested, imports `activity_ui` and calls `install(runtime, store=..., audit=...)`. That adds the observer, the `subscriptions/listen` presence handler, `ClientSessionMiddleware` inside the bearer check, the `/dashboard/api/activity` and `/dashboard/api/activity/stream` routes, and the `activity`/`clients` status fields. `/dashboard/api/status` always reports `extensions.activityUi`. With the UI on, finished calls are queued in memory and written by a background task in batches (up to 50 rows or 1 second) with one multi-row INSERT via `asyncio.to_thread`; the queue is flushed after the job runner closes at shutdown.

`scripts/bench_call_path.py` measures sequential tool-call latency through the HTTP app with the activity UI off and on.

## Request path

Direct call: `AI client → authenticated shared Hub → child MCP client → child MCP tool → metadata-only Hub audit log`

Investigation call: `AI client → job queue → fixed specialist roles → allowlisted child MCP tools → encrypted job result → coordinator summary`

Every exposed tool should map to exactly one child server and tool name. Use namespaced exposed names such as `serverId__toolName` to avoid collisions. A feature may expose tools from multiple child MCPs. Keep the initial design as a curated proxy; add cross-server composite tools only when a real workflow needs them.

## Failure handling and child selection

- **Isolation.** Each enabled child runs under its own `ChildSupervisor` (`children.py`): an asyncio task that owns the child's MCP client, its transport task groups, and its process. A child failure (a crash, a closed session, an error in the transport reader) ends only that task's session; it never reaches the service task that runs uvicorn, or another child. Child stdout is decoded with `encoding_error_handler="replace"`, so non-UTF-8 output becomes an unparsable line the SDK skips instead of an exception.
- **Start.** All children connect in parallel. Each attempt (start the process, MCP handshake, `list_tools`) is bounded by the child's `connectTimeoutSeconds` (default 120); a timed-out or failed attempt closes the process it started. The Hub serves once every child has connected or failed its first attempt, so startup takes at most the largest `connectTimeoutSeconds` (plus the SDK's few seconds to stop a hung process). A failed first attempt is logged (`server.connect.failed` or `server.list_tools.failed`), its tools are skipped (`route.skipped`), and the child is retried in the background like a lost one. With no available child tools, the Hub still exposes `hub__status`.
- **Reconnect.** When a connected child's session ends (the process exits, its stdout closes, or the transport fails), the Hub logs `server.disconnected` and retries after 1 s, doubling the delay after each failed attempt up to 60 s (`server.reconnect.failed` carries `retry_in_seconds`). A session that stayed up for less than 60 s counts as a failed attempt, so a child that crashes right after connecting is not restarted every second. A successful attempt logs `server.reconnected`, lists the child's tools again, and rebuilds the routes: a tool the child no longer lists is reported with `route.skipped` and calls to it are denied; a tool that appears is exposed, and `hub.tools.registered` lists the new set. Clients see changed tools on their next `tools/list`. Shutdown stops every supervisor and its process; nothing reconnects after it.
- **Calls while a child is down** return an error result immediately (`Child MCP <server-id> is reconnecting; retry shortly. request_id=<n>`) and are logged as `tool.call.failed` with `error_type=ChildUnavailable`; they never wait for the call timeout. The hot path checks only whether the child has a live client (a dict lookup).
- `hub__status` and the dashboard report detected sibling count, connected count, and each known child's state: `connected`, `connecting` (first attempt in progress), `reconnecting` (waiting to retry after a failed attempt or a lost session), `disabled`, `credentials required`, or `unavailable` (configured but not started). A child with unfilled `<SET_BY_USER>` placeholders in its private config is marked `credentials required`; its tools are not exposed. The built-in templates use empty values instead, so a child without Hub credentials still starts and uses its own local files (see [Configuration sources](child-mcp-compatibility.md#configuration-sources)). Detailed diagnostics are in the Hub log and the child's stderr log (`logs/children/<server-id>.log`, see [security-and-logging.md](security-and-logging.md)).
- Each call is limited by the child's `timeoutSeconds` (default 60); a timeout is logged as `tool.call.failed` with `error_type=TimeoutError`. A failure raised as an exception group is logged by its first leaf exception, so `error_type` names the cause.
- The Hub exposes one MCP prompt per connected child, named after its server ID. Clients that support prompts show it as a slash command (the exact format is client-defined); it tells the Agent which Hub tools belong to that child and includes `docs/mcps/<server-id>.md`.
- On connect, the Hub sends server instructions, essentials first: a summary under 512 characters (`INSTRUCTIONS_SUMMARY` in `server.py`), the tool list per child, and then [client-rules.md](client-rules.md), read at startup. Clients may truncate them (Claude Code cuts at 4,096 characters), so only the tail of the rules can be lost. Clients that ignore server instructions get the same rules from the always-on rule installed by [connecting-a-client.md](connecting-a-client.md) step 7.

## Local child servers

Children run over `stdio`. The Hub launches each one with an argument array (never a shell string) in the child's `cwd`, passing only the MCP SDK's default safe variables, the `inheritEnv` names, and the child's `env` values. Child repositories are expected to sit next to this repo, so configs reference them as `../<repo>`. The Hub resolves relative paths in memory; tracked config never contains machine paths. A private Hub manifest can override each known child or feature, and `enabled: false` takes precedence over discovery. The source reader is a separate child repo; it reads only project roots registered by alias in its own private configuration. The Hub separately validates those aliases and environments for job requests. An explicit `MCP_HUB_CONFIG` retains the private-manifest-only behavior.

## Shared Windows service

`scripts/hubctl.ps1 install` prepares a per-user Task Scheduler task named `mcp-hub` with limited privileges and starts `mcp-hub-service` through `pythonw.exe` without a console window, independently of terminal windows and battery power. Before every start, `hubctl` syncs the locked environment and runs `python -m mcp_hub.preflight --install`, which checks each enabled child's declared runtime (installing or upgrading it with winget when needed) and runs the child's own dependency step. Child `prepare` commands get the same environment as the child at runtime (`children.child_environment`: the MCP SDK's safe defaults, `inheritEnv`, and `env`), and executables are resolved only from absolute `PATH` entries, never the working directory (`preflight.find_executable`). The service binds only to loopback (`127.0.0.1:8765`, from `config/private/service.json`), requires a bearer token for MCP, and keeps the original per-client stdio launcher. HTTP-capable clients can use `scripts/http_headers.ps1`; other clients use `scripts/start.ps1 -Bridge`, which forwards stdio MCP messages to the shared service. The authenticated dashboard shows jobs and child state; with the activity UI (`-Ui`) it also visualizes live child MCP tool activity. A second logon task, `mcp-hub-status`, opens the desktop status app (`desktop/`), which polls `/health` and `/dashboard/api/status` with the bearer token ([desktop-app.md](desktop-app.md)). Setup and migration are in [the shared-service runbook](operations/shared-agent-hub.md).

The job runner allows two active jobs, at most 20 queued jobs (`hub__submit_issue` and `hub__provide_job_input` return an error when the queue is full), a 15-minute investigation window, and 30 child-tool calls per job. Jobs missing an environment wait for validated input. Specialists are offered only their role's tools that the child marks read-only plus the Hub's encrypted cache-refresh allowlist (`jobs/policy.py`). A failed tool call (unknown or withheld tool, schema mismatch, child exception or error result, call cap) goes back to the model as an error tool message, so the specialist continues; only a provider error or its round limit ends it, and evidence it already stored is kept. When the window ends, unfinished specialists are cancelled and contribute the evidence they stored; the coordinator then gets up to 90 seconds (`COORDINATOR_SECONDS`) to summarize what exists, otherwise a fallback summary lists the findings and evidence IDs, and the job ends `partial`. A job waiting for write approval releases its active slot and takes one again after approval (specialists already running in that job continue); the wait still counts against its 15-minute window. While a job runs, its store and DPAPI work (events, child results, details, summaries, approvals) runs via `asyncio.to_thread`; only start-up recovery and cancellation bookkeeping run inline. `hub__get_job` returns the first 100 timeline events and every evidence ID of the job. On restart, active investigation state is marked interrupted and never replayed. A pending write can remain awaiting approval until 15 minutes after the job was created, then the job becomes `partial` (`approval.expired`); once approved, the exact stored operation is executed once and the job reports partial because its model investigation is not replayed. Dashboard approval uses a session cookie; the MCP alternative requires a one-time code visible in the dashboard. The approval routes refuse the bearer token, so only a paired browser can see the code or approve, and every write in a job waits for its own approval (see [security-and-logging.md](security-and-logging.md)).

Each child MCP has a contract at `docs/mcps/<server-id>.md`; see [mcps/README.md](mcps/README.md). To add one, follow [adding-a-child-mcp.md](adding-a-child-mcp.md).
