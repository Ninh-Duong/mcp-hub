# PR Companion MCP contract

- Repository: sibling `../mcp-pr-companion` (Node 20.12+). Its own rules: `../mcp-pr-companion/AGENTS.md`.
- Hub discovers this supported sibling automatically from the relative path. No private Hub config is needed unless overriding or disabling it; `hub__status` reports detection and connection.
- Transport: local stdio process launched by the Hub as `node bin/cli.js server` in the child repo (`config/private/mcps/mcp-pr-companion.json`, template `config/mcps/mcp-pr-companion.example.json`). `bin/cli.js` runs `npm ci` / `npm run build` when needed; `prepare` does this explicitly. On Windows, `inheritEnv` includes `APPDATA`, `LOCALAPPDATA`, `PATHEXT`, and `COMSPEC` for npm.
- Configuration: follows [Configuration sources](../child-mcp-compatibility.md#configuration-sources). The private config's `env.CENTRAL_CONFIG_PATH` points the child to that same file (relative to the child repo root); the launcher `bin/cli.js` reads its `bitbucket` block: `email` → `BITBUCKET_EMAIL`, `api_token` → `BITBUCKET_API_TOKEN`, `workspace` → `BITBUCKET_WORKSPACE`, `repository` → `BITBUCKET_REPOSITORY`, `allowed_emails` → `ALLOWED_EMAILS` (string or list). Priority per value: `env` > the `bitbucket` block > the child's `.env` > default; empty values fall back to `.env`, and a missing or unreadable Hub file is logged as a warning (error code only) and `.env` is used. Other settings stay in the child's `.env` or the config's `env` (`TICKET_PREFIXES`, `AUTO_SYNC_ON_START`, `PRIVACY_*`, `AI_CONTEXT_*`, `DEBUG`). Required for the Config tab: `bitbucket.email`, `bitbucket.api_token`, `bitbucket.workspace` (declared in the child's `hub-requirements.json`). Agents must not read `.env`. `BITBUCKET_REPOSITORY` supplies defaults to `list_my_open_prs`, `list_synced_prs`, and `sync_my_open_prs`, and is used by `AUTO_SYNC_ON_START`, `node bin/cli.js check`, and `node bin/cli.js sync <mode>`. Optional non-secret overrides can go in the child config's `env`, e.g. `env.PRIVACY_FILE_PATH_MODE`; never set it to `full` under the Hub because that returns real paths.
- `timeoutSeconds` is 300 because the first sync of a large PR downloads a full diff and the sync tools can process many PRs.
- Data at rest: everything in the child's `ai-context/`, including revision data, comment snapshots, and last-refresh metadata, is encrypted (AES-256-GCM, key derived from the repository UUID). Tools that read local data unlock the relevant repository with a Bitbucket access check; a successful unlock is cached for 60 seconds per repository. Details: `../mcp-pr-companion/docs/ENCRYPTION.md`.
- Privacy: `PRIVACY_REMOVE_AUTHOR` defaults to `true`, so comment display names are hidden. Set the child deployment's `env.PRIVACY_REMOVE_AUTHOR` to the string `false` to return sanitized author names; do not change the shared template default. Comment text and paths remain sanitized, and the child returns no severity field or inferred severity.
- Canonical storage groups are `open`, `draft`, `merged`, and `declined`. The group reflects the last successful sync; draft PRs have Bitbucket state `OPEN` and the draft flag set. Readers also search legacy status-less paths. When status or draft state changes, a successful sync publishes and validates the encrypted revision before migrating retained revision directories from old paths. Cross-volume copies use `readSecure` / `writeSecure`, verify decrypted contents, and preserve revision directory times for retention sorting. A fresh validated revision replaces an old active revision with the same ID. Failed migration or a conflicting history destination leaves the source readable for a later retry; unresolved conflicts remain there until the destination is repaired.
- `AUTO_SYNC_ON_START=true` makes each server launch sync the configured account's open PRs in the background.
- Bitbucket requests are read-only `GET`s. `fetchWithRetry` retries 429 and 5xx responses twice; other responses are not retried. No tool writes to Bitbucket.

## Tools

All tools return MCP text content containing Markdown or JSON. Errors are marked `isError` and text begins `Error:`. The child sanitizes returned content and error text. The eleven exposed aliases below match the names in `config/hub.example.json`.

| Hub tool | Inputs and defaults | Behavior, output, and side effects | MCP annotations |
|---|---|---|---|
| `pr__get_pr_context_pack` | Required `pr_url`; `refresh=false`; `include_file_table=false` | Checks current source/destination commits, state, and draft status on every call by default (`FRESHNESS_TTL_SECONDS=0`); `refresh=true` forces a full sync. Syncs missing/changed revisions before returning and reuses fetched head metadata. Returns report context plus live approvals/build results and a review-thread summary. Refreshes every comment page independently of revision commits and writes a complete sanitized review snapshot to encrypted local storage. If the comment fetch is incomplete, preserves the last complete snapshot and reports the sanitized warning and snapshot age. Approvals/build statuses remain live and are never stored in the review snapshot. The MCP does not infer review severity. | `readOnlyHint=false`, `openWorldHint=true` |
| `pr__search_pr_files` | Required `pr_url`; optional `path`, `language`, `status` (`added\|modified\|deleted\|renamed`), `change_kind`, `risk_tag`; `limit=50` (1–200) | Checks freshness and syncs a missing/changed revision before listing files. Returns JSON `{total, files, warning?}`; path substring matching is case-insensitive and uses sanitized paths. | `readOnlyHint=false`, `openWorldHint=true` |
| `pr__get_pr_file_context` | Required `pr_url`, `file_id` (string or nonnegative integer); `offset=0`; `max_chars=16000` (500–100000) | Checks freshness and syncs a missing/changed revision before returning Markdown for one file and a sanitized diff page; if more remains, ends with `continue with offset N.` | `readOnlyHint=false`, `openWorldHint=true` |
| `pr__get_pr_file_changes` | Required `pr_url`, `file_id` (string or nonnegative integer); `include_patch=true`; `offset=0`; `max_chars=16000` (500–100000) | Checks freshness and syncs a missing/changed revision before returning JSON `{change, patch?, warning?}` where `change` includes classification/evidence, risk level/tags/evidence and symbols; included `patch` is `{text,total_chars,next_offset}`. | `readOnlyHint=false`, `openWorldHint=true` |
| `pr__get_pr_comments` | Required `pr_url`; `include_resolved=true`; `offset=0`; `limit=50` (1–200) | Checks freshness, then reads the latest complete encrypted review snapshot; it does not refetch comments for each page. Returns `{snapshot_id,fetched_at,source_commit,total,complete,warnings,refresh_attempt?,comments,next_offset}`. Each row has a sanitized text preview, `text_total_chars`, and `text_next_offset` when truncated. A failed refresh with a retained snapshot is identified in `warnings` with its original time/source and age. If the initial refresh is incomplete and no complete snapshot exists, returns `complete=false`, `snapshot_id=null`, nullable snapshot metadata, no rows, and the sanitized warning. Author names are omitted by default and included only when `PRIVACY_REMOVE_AUTHOR=false`. | `readOnlyHint=false`, `openWorldHint=true` |
| `pr__get_pr_comment` | Required `pr_url`, `comment_id` (nonnegative integer); optional `snapshot_id` (required when `offset>0`); `offset=0`; `max_chars=16000` (500–100000) | Checks freshness and reads one comment from the latest complete encrypted snapshot. Returns `{snapshot_id,comment,text,total_chars,next_offset,warnings}`; pass the returned `snapshot_id` on every continuation. If the snapshot changed, restart at `offset=0` with the new ID instead of combining body versions. Author names follow `PRIVACY_REMOVE_AUTHOR`; unknown IDs return a sanitized actionable error. | `readOnlyHint=false`, `openWorldHint=true` |
| `pr__list_synced_prs` | Optional `repository` (`workspace/repo`; omitted uses every `BITBUCKET_REPOSITORY` entry); optional `status` (`open\|draft\|merged\|declined`); `offset=0`; `limit=50` (1–200) | Lists locally synced revisions after unlocking each repository. Returns JSON `{total, prs:[{pr_url,repository,id,title,pr_status,updated_at}], next_offset}`. It does not discover or refresh PRs from Bitbucket. | `readOnlyHint=true`, `openWorldHint=true` |
| `pr__list_my_open_prs` | Optional `repository` (`workspace/repo`; omitted uses every `BITBUCKET_REPOSITORY` entry) | Discovers open PRs authored by the configured account. Returns JSON `{total,prs:[{pr_url,repository,id,title,is_draft,source_branch,target_branch,updated_on,local}]}`; `local` is `missing`, `cached`, or `outdated`. Live Bitbucket reads; no cache write. | `readOnlyHint=true`, `openWorldHint=true` |
| `pr__sync_my_open_prs` | Optional `repository` (same default as above); `force=false` | Discovers and syncs the account's open PRs, three at a time. Without force, skips PRs whose commits, state, draft flag, and storage location match, judged from the discovery data, so unchanged cached PRs cost no extra request. Returns JSON `{total,synced,unchanged,failed,prs:[{pr_url,id,title,status,ticket,overall_risk,files_changed,updated_on,error?}]}`. | `pr__check_bitbucket_connection` | No inputs | Read-only health tool. | `pr__get_pr_sync_status` | Required `pr_url` | Checks freshness and syncs a missing/changed revision before returning `{synced,revision,updated_at,source_commit,target_commit,ai_reading_mode,pr_status,stats,warning?}`. | `readOnlyHint=false`, `openWorldHint=true` |

All tools that touch local encrypted data (including list and file readers) require repository unlock. The successful access check is cached for 60 seconds per repository. `check_bitbucket_connection` is a general credential/allowlist check; it does not establish access to every repository. PR-specific readers check the head on every call by default and may sync/write the encrypted cache; a positive `FRESHNESS_TTL_SECONDS` opts into a bounded freshness window. `get_pr_context_pack` refreshes comments on every report, regardless of commits. `get_pr_comments` and `get_pr_comment` read the saved snapshot and do not fetch comments per page. The snapshot contains sanitized comment data only, not approvals, build statuses, or inferred severity.

## Caching (contract the child must meet)

`../mcp-pr-companion` must implement these behaviors; agents may rely on them.

- PR-specific reads check freshness on every call by default (`FRESHNESS_TTL_SECONDS=0`). A positive value opts into a window; `get_pr_context_pack(refresh=true)` forces a full sync. The check time is stored in the encrypted `current.json`. With the default, unchanged PRs reuse the revision without downloading commits/diffs; changed revisions sync before file data is returned.
- `pr__sync_my_open_prs` skips cached, unchanged PRs using the discovery data, without a per-PR metadata request.
- The current-user lookup is cached per process. When the author-filtered listing is empty, the fallback that scans open pull requests reads at most 2 pages; if it is cut off, `pr__list_my_open_prs` and `pr__sync_my_open_prs` add a `warnings` array and the listing still counts as complete.
- The context pack refreshes all comment pages and summarizes open review threads. `pr__get_pr_comments` reads the saved complete snapshot and returns bounded previews; after a partial first fetch with no prior complete snapshot it reports `complete=false` and no rows. `pr__get_pr_comment` pages long bodies. On a later partial refresh, the prior complete snapshot remains current and the sanitized warning/age are returned. Author names stay hidden by default; `PRIVACY_REMOVE_AUTHOR=false` opts a deployment into sanitized author display names. The child does not assign severity; agents assess importance from comment text.

## Hub result cache

Shared rules: [Hub result cache](README.md#hub-result-cache). Defaults here: 300 s for `pr__check_bitbucket_connection` only. Every tool that returns PR data has no Hub TTL, because this child forbids in-memory caching of PR data; its own encrypted cache and freshness check handle repeats.

## CLI sync and cache migration

To sync historical PR states, the user runs `node bin/cli.js sync <open|draft|merged|declined|all>` in the child repo. This command scans every page for the selected states and filters to PRs authored by the configured account across `BITBUCKET_REPOSITORY`; `open` excludes drafts and `all` combines the four groups. It writes the encrypted local cache. An interrupted pagination run is marked incomplete and exits with an error code; rerunning the command can complete it. The MCP `sync_my_open_prs` remains open-only.

After a pre-encryption file is detected, the reader treats that PR as unsynced. A later successful sync writes encrypted data and prunes old plaintext revisions. The user can instead run `node bin/cli.js purge-plaintext` to delete all non-encrypted files under `ai-context/` without network access, then sync again. For interrupted status-directory migration, the newly validated revision is retained and the old encrypted directory remains readable; a subsequent successful sync retries migration even when the PR is unchanged. A same-named historical revision is removed from the source only after its destination decrypts to the same content. Never inspect or copy `ai-context/` with file tools or scripts; use the MCP tools.

## Working guidance

- Cache first: use `pr__list_synced_prs` to find already cached PRs and `pr__get_pr_sync_status` to check one, then `pr__get_pr_context_pack` and the file tools. Call `pr__list_my_open_prs` only to discover PRs that are not cached, and pass `refresh=true` only when the cache is stale or the user asks.
- To sync open PRs when the user asks, call `pr__sync_my_open_prs` with a repository when useful and show its `prs` as a table. Include failed rows and their `error`.
- Never repeat an identical call within a task, and call `pr__check_bitbucket_connection` only to explain a failed call.
- PR-specific file readers check the latest PR metadata and automatically sync a missing or changed revision before returning file data. If the metadata check is unavailable, they report that cached data may be stale. Start with the Read Strategy and open only `Read next` file ids, then `Optional` if needed. For re-review, open the ids listed in “Changed since last sync”.
- For review feedback, start with `pr__get_pr_context_pack`, which refreshes review comments even when commits have not changed. Use `pr__get_pr_comments` to page the saved complete comment list, then `pr__get_pr_comment` to read long bodies by `text_next_offset`/`next_offset`; pass the returned `snapshot_id` on each continuation and restart if it changed.
- Keep paging with `next_offset` or `continue with offset N`; do not raise `max_chars` just to read a large PR at once.
- If the context pack begins `Note: could not check Bitbucket…`, the result is cached and may be stale. State that when using it.
- A `No access` error means the access check failed (credentials, `ALLOWED_EMAILS`, repository read access, or network). Tell the user; never work around it or read encrypted files directly.
- Sanitized paths and text are intentional; do not try to recover the original values.

## Hub integration and diagnostics

- The Hub smoke check uses `pr__check_bitbucket_connection` and expects `connected: true`. Without credentials the child still starts and this tool returns `No Bitbucket credentials`, which the smoke check shows as `WARN`. Child self-check `node bin/cli.js check` separately checks Node, dependencies, build, and required settings, including `BITBUCKET_REPOSITORY`, and prints their sources on its Config line; it is not an MCP tool.
- Child logs are in `../mcp-pr-companion/Logs/mcp-server.log` (launcher errors use `[LAUNCHER]`). Hub events are in `logs/mcp-hub.jsonl`.
- `Error: No access: Bitbucket rejected the credentials (HTTP 401)` indicates invalid credentials; fix them where `config_source.credentials` says (`hub`: the `bitbucket` block, `local`: the child's `.env`). `Failed to fetch PR metadata: HTTP 403` generally indicates a missing `read:pullrequest` or `read:repository` scope. `Error: No access: this account cannot read <ws>/<repo>` means the account lacks repository access. A network failure prevents unlocking the encrypted cache.
- An `Unencrypted ai-context file` error indicates pre-encryption data; run `purge-plaintext` or resync that PR.
